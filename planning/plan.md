# Build plan

## 1. Choices

- **Runtime:** Python 3.10+ with SQLite, `jsonschema` and an HTTP client; use a pinned dependency lockfile and test the declared supported Python versions, keeping setup close to the class prerequisites.
- **Interface:** a CLI, provisionally `python3 -m access_intake`, with `intake PATH`, `queue`, `work`, `history DOCUMENT`, `resume`, `retry DOCUMENT --force`, `export` and `accuracy`; separate reader processes can inspect committed work during intake.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; all provider calls use saved replies or injected errors behind a transport seam, with outbound sockets forbidden. No test reads or requires `API_KEY`.
- **Model provider:** implement a configurable HTTP adapter for OpenAI Responses, non-streaming structured extraction, selected through `PROVIDER`, `MODEL`, endpoint and request settings; only an explicitly selected live run reads `API_KEY`. Verify the current official provider protocol and supported model before implementing step 8; save the supported model ID and complete request configuration in evidence. Mock mode is the default for tests and development examples.

These are implementation choices, not additional business requirements. This document is a plan only: fixture paths, commands and tests below are proposed, not existing or executed work. The existing generic canned reply is not an extraction oracle. Do not edit the spec or create code, fixtures, tests or deliverables in this planning task.

### State, provenance and operating design

Use a local SQLite database on one host with multiple CLI processes sharing the same database. This is the proposed supported shared-operation deployment; cross-host SQLite/network filesystems are outside the verified deployment. Use short transactions, a unique document identity and append-only attempt history. Never hold a database transaction across a model request. Each admitted revision captures the original bytes once, its decoded message, filename and SHA-256; hash and extract the same captured bytes. Directory inputs are flat and filenames include `.json`. Detect duplicate basenames in an intake before admitting them. Do not silently merge documents by request ID.

Give each attempt a unique ID, document generation, source hash, processing fingerprint, policy hash, timestamps and processing state (`pending`, `running`, `succeeded`, `failed`, `interrupted`). Claim work transactionally with an expiring lease and fencing token; a replaced revision or expired worker cannot overwrite a newer generation. Define “latest” as the latest admitted generation, rather than whichever provider call returns last. Queue and extraction views read one committed database snapshot and include the same attempt/source provenance. Completed older results stay in history; while a replacement is pending, the work view clearly identifies it and labels any displayed prior result as earlier work. Review statuses remain the policy's statuses, separate from processing states.

Fingerprint provider, model ID, endpoint, prompt, schema, extraction/routing version, request parameters and policy bytes; include fixture identity/content for mock runs. Credentials, local database path, worker count and display settings do not alter extraction identity. Conservatively refresh all documents on any relevant setting or policy change; a policy-only refresh may initially rerun extraction for simplicity. Reuse only unchanged successful results. Leave unchanged failures visible until explicit `retry DOCUMENT --force`; forced retry creates a new attempt even after success. Retain attempts and captured source revisions without pruning in this exercise. Retain producing provenance when reusing a result.

Start with four workers, configurable concurrency and pacing, a configurable finite request timeout and no hidden automatic retries. Rate-limit, timeout and unavailable replies become actionable per-document failures; `resume` recovers interrupted/pending work and the documented retry command retries failures. These defaults are tunable choices, not throughput promises. Lease expiry must exceed the request timeout plus commit margin and be testable with an injected clock. A crash may cause a duplicate external call; fencing prevents duplicate current results. Do not claim exactly-once provider execution.

The database-backed CLI is the live inspection interface. Export both deliverable files from one database read snapshot into an immutable generation directory, then switch a `deliverables` symlink atomically. CLI readers resolve the generation once before opening either file; document this paired-read protocol for external readers. Keep export generations separate from attempt history. Initial intake must finish every admitted document before a final submission export: no invented pending review status in the final files. Test crashes before and after generation publication. A later batch only upserts its members; omission never deletes earlier documents.

An error object will contain a stable category, safe explanation, attempt/source reference and exact retry command. Never persist authorization headers or raw credential-bearing provider errors. Use allowlisted diagnostics and redaction in operational logs and request evidence. Queue output carries document ID, attempt ID, source hash, processing state and, when available, policy status/owner/next action. `response_source` is `mock` for fixtures and a documented provider/model string for successful live extraction; failed attempts also identify the attempted configuration without implying a successful response.

### Decisions still needing human review

The user approved one quoted purpose sentence per message and literal exact-match scoring. The source expectations below implement that choice. Issue wording and evidence-array order have no canonical business wording: assert the required issue meanings and exact substring evidence, and report literal array matches separately.

The sample-supported cases below are specified; these broader cases remain open. In particular, a generic override detector cannot be established by one canned attack. Review prompt and source-as-data handling as well as testing the supplied attack.

Input outside the promised format (Q-20–Q-23), rename/collision semantics beyond the flat-directory choice (Q-18), and additional redaction/capture requirements (Q-61/Q-62) need operator/facilitator agreement if encountered. Plan to reject invalid JSON/UTF-8 or non-string messages visibly at intake without a fabricated extraction or invented hash; exact queue treatment is unresolved. Do not silently truncate long inputs or infer relative dates. No performance deadline, live-accuracy threshold, multi-host support, executable approvals or directory of named system owners is implied. Preserve all R IDs; grouped requirements are checked with subcases rather than rewriting the spec (Q-66).

## 3. Test plan

All paths in this section are future fixtures. `M/name.json` means `tests/mock_responses/name.json`. For steps 1–7, each reply is a complete provider-neutral envelope with `state` (`completed`, `refused` or `interrupted`), `output_text` and optional refusal/error detail. The mock returns this envelope through the same interface the real adapter will implement; validation checks completion before parsing output text. The `M/provider-*.json` fixtures in step 8 represent native protocol replies whose exact envelope fields must be verified from official documentation before they are authored. Inject transport errors explicitly; a delay/barrier controls a named reply and is not itself a model reply. `E/name.json` below means a separately authored expected extraction, never copied from a run. Use full schema keys, string arrays for quotes/issues and explicit nulls. Success means `error=null`; failures mean `extraction=null`. Every row is owned by exactly one numbered step above. Bare supplied filenames mean `materials/requests/FILENAME`; authored variants are specified completely below as message text or deterministic edits to a read source, and retain their stated filename in isolated temporary case directories. Artifact-only checks use outputs generated from these named sources; they do not invent additional request inputs. No fixture is authored from a measured application result.
